# Workflow — цикл работы, метафайлы, редизайн

## 1. Цикл одной задачи (чанка)

```
требования → план → правка → проверки → коммит → пуш → CI → живая сверка → отчёт
```

1. **Требования.** Перечитай сообщение заказчика построчно и выпиши
   чек-лист: каждая часть, объём, формат, имена, даты, запреты.
   «Закомитить всё» = два письма, а не одно; «сделай как у нас» = файл
   правила открыт и перечитан.
2. **План.** Коротко: какие чанки, в каком порядке, что куда.
   План не согласование ради — он ловит половину ошибок до правок.
3. **Правка.** Файл читается в текущей сессии перед любым Edit
   (память о содержимом между сессиями не живёт — проверять глазами,
   не по памяти).
4. **Проверки** — `ci-gates.md` §1–3.
5. **Коммит и пуш** — `commits.md`.
6. **CI и живая сверка** — `ci-gates.md` §5.
7. **Отчёт** — 2–4 строки: что сделано, хеш коммита, что дальше.

Чек-лист из п. 1 закрывается до конца: «осталось мелочь» = задача
не закрыта. Найденный по дороге баг — отдельным чанком сразу или
записью в BACKLOG, но не «потом».

## 2. Старт сессии (чек-лист)

```bash
git fetch origin && git status -sb && git log --oneline -5
```

- Рабочая копия = зеркало GitHub, дерево чистое; расхождения
  разбираются до правок (force-push запрещён).
- Перечитать хвост SESSIONS, открытые пункты BACKLOG и паспорт
  проекта — не делать сделанное заново и не предлагать отклонённое.
- Проверить, что с прошлого раза не осталось незапушенного
  (после обрыва работы «ahead N» бывает легитимным: сначала
  fetch/merge, потом работа).

## 3. Метафайлы (роли не смешивать)

| Файл | Роль | Что туда |
|---|---|---|
| `PROJECT-META.md` | Паспорт: что это, почему так, рецепты отката | Карта проекта, журнал решений с датами, принципы. Не раздувать: паспорт, не дневник |
| `SESSIONS.md` | Журнал по датам | Что сделано за сессию, цепочки хешей, инциденты и выводы |
| `BACKLOG.md` | Задачи и идеи | Пункты с причиной и статусом ☐ ждёт / ▶ в работе / ✅ сделано (хеш). Каждый пункт разблокируется явной командой заказчика |
| `rules/` | Правила работы | Этот комплект; меняется отдельным чанком с причиной |

Метафайлы — безличные заметки: факты, решения, причины. Без обращений,
без пересказа разговоров, без личных данных. Любое исследование с
выводом — сразу в метафайл (оно теряется, если живёт только в чате).

«Не делается без явной отмены» — отклонённые решения фиксируются
в BACKLOG с датой, чтобы их не предлагали заново каждую сессию.

## 4. Редизайн старого сайта (порядок для этого проекта)

Контент и структура старого сайта — **источник истины**. Редизайн
меняет визуал, а не факты.

1. **Инвентаризация до первой правки.** Список всех страниц, разделов,
   текстов, картинок, скриптов старого сайта — в `PROJECT-META.md`
   (карта) + таблица «страница → перенесена? → коммит». Это страховка
   от классической потери: старая страница выпала из редизайна и
   её никто не заметил.
2. **Архивная ветка.** До первых правок: `git branch archive/old-design`.
   Старая версия всегда доступна целиком, «а как было» не
   восстанавливается по памяти.
3. **Постранично.** Чанк = одна страница (или одна секция крупной):
   контент переносится дословно, визуал — новый. Никаких
   «перенесу потом», чанк закрывается с живой проверкой страницы.
4. **Карта редиректов.** Если меняются адреса страниц — таблица
   старый → новый в PROJECT-META; внешние ссылки и закладки не должны
   умирать молча.
5. **Ассеты.** Старые картинки не теряются: неиспользуемые помечаются,
   не удаляются (решение об удалении — отдельный чанк с причиной).
6. **Приёмка.** После каждой страницы: рендер на 5 ширинах, ссылки
   с неё и на неё, текст вслух на слоп (`anti-slop.md` §1).
7. **Финал редизайна.** Полная сверка с инвентаризацией: каждая
   строка таблицы закрыта или осознанно исключена с причиной в метафайле.

## 5. Отчёт по чанку

```
сделано: … ; коммит <хеш>; CI success, прод проверен (что именно);
дальше: …
```

Отчёт нужен для контроля: хеш позволяет в любой момент сверить,
что правка доехала до GitHub и прода.
